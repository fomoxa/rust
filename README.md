# fomoxa-rust

Fomoxa in Rust, written from the specification: the runtime that carries Fomoxa
messages over TCP or UDP - framing, schema handshake, heartbeat, and a tick loop
that never blocks.

No dependencies. No async runtime. No background threads. No engine.

```toml
[dependencies]
fomoxa-net = "0.2"
```

## What this is, and what it answers to

The [protocol specification](https://github.com/fomoxa/specification)
is the authority here, and nothing else is:

| Document | What it fixes |
|---|---|
| RFC-0001 | What Fomoxa is, and the five design decisions behind it |
| RFC-0002 | The byte layout: primitives, string, bytes, model, array, enum, version differences |
| RFC-0003 | Conformance: the test vectors an implementation must pass, all of them |
| [Implementation guide](https://github.com/fomoxa/implementation-guide) | The layer above: framing, handshake, heartbeat, the transport contract |

Where this crate and any other Fomoxa SDK disagree, the RFCs decide, and both
sides agreeing with each other proves nothing. Every behaviour below is written
against a clause, and the clause is cited.

This crate is one layer of three, and only one:

```
  your application
        |
  codec         RFC-0002 - Model <-> bytes                  generated by fomoxac,
                                                            NOT in this crate
        |
  runtime       implementation guide - frames, handshake,   src/frame.rs, src/session.rs,
  (this crate)  heartbeat, tick loop, events                src/connection.rs, src/server.rs
        |
  transport     TCP or UDP, or one you write yourself       src/transport/
```

A message payload is opaque here, from the transport all the way up to the event
handed to your application. Nothing in this repository reads a byte of it.

## Quick start

### Client

```rust
use fomoxa_net::{Config, Connection, Event, TcpTransport};

let transport = TcpTransport::connect("127.0.0.1:9321")?;
let mut connection = Connection::new(transport, schema(), Config::default());

loop {
    for event in connection.tick_now() {
        match event {
            Event::Ready => { /* only now may you send */ }
            Event::Message { id, payload } => handle(id, payload),
            Event::Disconnected(reason) => return,
            _ => {}
        }
    }
}
```

`schema()` is four lines over what `fomoxac` generated - see
[Where the codec is](#where-the-codec-is).

### Server

```rust
use fomoxa_net::{Config, Event, Server, TcpListenerTransport};

let listener = TcpListenerTransport::bind("127.0.0.1:9321")?;
let mut server = Server::new(listener, schema, Config::default());

loop {
    for seen in server.tick_now() {
        match seen.event {
            Event::Ready => println!("{} accepted", seen.peer),
            Event::Message { id, payload } => handle(seen.peer, id, payload),
            _ => {}
        }
    }
}
```

`examples/client.rs` and `examples/server.rs` are two runnable processes doing
exactly this. Start the server first:

```
cargo run --example server
cargo run --example client
```

## Where the codec is

It is not here, and that is deliberate.

`fomoxac` generates the RFC-0002 codec runtime - `Writer`, `Reader`,
`DecodeError`, `Limits` - into your own project, together with a codec per
message and the fingerprints below. There is exactly one implementation of
RFC-0002 in Rust, it lives in the generator, and its conformance is proved there:
`fomoxac/tests/vectors.rs` runs the committed cross-SDK vectors through the real
generated codecs.

A second copy in this crate would be a second implementation of RFC-0002 in the
same language. Two encoders drift, and RFC-0001 §6.1 is explicit that the drift
is silent - both ends still decode, the bytes just stop matching. So this crate
carries none.

What you hand this crate instead is two things `fomoxac` also generates:

- **the message id**, for `send` and for `Event::Message`;
- **the schema table** - `FOMOXA_SCHEMA_FINGERPRINT`, and per message its id,
  its fingerprint and its prefix chain - which becomes a `Schema` and is what the
  handshake compares.

```rust
use fomoxa_net::{MessageSchema, Schema};

let schema = Schema::new(
    generated::FOMOXA_SCHEMA_FINGERPRINT,
    generated::FOMOXA_MESSAGES
        .iter()
        .map(|message| MessageSchema::new(message.id, message.fingerprint, message.prefixes))
        .collect::<Vec<_>>(),
)?;
```

Encoding is then your generated codec's job, and this crate only ever sees the
bytes it produced:

```rust
let mut writer = generated::Writer::new();
GameMessageStateCodec::encode(&mut writer, &state);
connection.send(generated::GAME_MESSAGE_STATE_MESSAGE_ID, writer.as_slice())?;
```

### The demo project

`examples/demo/` is that whole path, committed and real rather than described:

```
examples/demo/
  fomoxa.toml                  src = "src", out = "src/generated"
  src/models/game.rs            the models you annotate - the only file written by hand
  src/schema.rs                 FOMOXA_MESSAGES -> Schema, the four lines above
  src/generated/                what `fomoxac generate` wrote, committed as-is
    runtime.rs                    Writer, Reader, DecodeError, Limits
    handshake.rs                  fingerprints, prefix chains, message ids
    game_message_state.rs         one file per model per codec
    player_input_input.rs
    vector3_state.rs
    vector3_input.rs
  .fomoxa/schema.json          the build-time record fomoxac compares against
```

The models mirror RFC-0002 §15's worked example - a `u32`, a `string`, a nested
`Vector3` of three `f32`, another `u32` and a `bool` - plus a `PlayerInput` going
the other way. `GameMessage::last_seen_at` is deliberately *not* annotated: it is
a field of your type that no codec carries, and `tests/demo.rs` asserts it
arrives as `0` on the far side. Your types stay yours (RFC-0001 §6.6).

Regenerate after editing a model, from that directory:

```
fomoxac generate
```

Two things to know if you do. The tree is committed exactly as `fomoxac` writes
it, and `rustfmt` would otherwise reformat it into a permanent disagreement with
the generator - which is why the examples and `tests/demo.rs` mount it through a
`macro_rules!` wrapper that `rustfmt` cannot follow. And no CI job here checks the
tree for freshness: that would mean installing a generator from outside this
repository, and this repository builds on its own.

## The runtime - wire format

Every byte the runtime puts on a transport is a frame, and every frame starts
with a type byte.

```
  0  DATA        11-byte header, then the payload
  1  PROBE       one byte, no body
  2  ACK         one byte, no body
  3  HANDSHAKE   5-byte header, then an opaque payload
```

### Data frame

```
  +----+----+----+---------------+---------------+---------------------+
  | 00 | 43 | 59 | message id    | payload len   | payload             |
  |    |'C' |'Y' | 4B u32 LE     | 4B u32 LE     | = payload len       |
  +----+----+----+---------------+---------------+---------------------+
   ^0    ^1   ^2      ^3-6            ^7-10           ^11..
```

The message id is a message *type*, assigned by your schema. It is not a
sequence number, and nothing here reorders, retransmits or deduplicates.

### Handshake frame

```
  +----+---------------+----------------------------+
  | 03 | payload len   | handshake payload          |
  |    | 4B u32 LE     | = payload len              |
  +----+---------------+----------------------------+
```

### Framing on a byte stream vs. a packet

On a stream, frames sit back to back with no separator, and the decoder works
incrementally - feed it one byte at a time if that is what arrives. **Any
framing violation on a stream is fatal**: there is no resynchronisation point, so
the decoder is poisoned permanently and the session closes.

On a packet transport, one packet holds exactly one frame - a short packet or a
packet with bytes left over is broken. **A framing violation there is not
fatal**: drop that packet and carry on, because a single datagram cannot corrupt
shared parsing state. The asymmetry is deliberate.

## The handshake

The client sends one hello. The server is the only side that compares anything,
and it answers with a single verdict byte. The usual case is one round; exactly
one case needs a second.

```
  CLIENT                                         SERVER
    |  -- HANDSHAKE(hello) ---------------------> |
    |                                             |  1. frame check
    |                                             |  2. version check
    |                                             |  3. fingerprint check
    |  <-- HANDSHAKE(verdict, 1 byte) ----------- |  decided
    |  <-- HANDSHAKE(4 = need more, list) ------- |  undecidable
    |  -- HANDSHAKE(prefix answers) ------------> |
    |  <-- HANDSHAKE(verdict, 1 byte) ----------- |
```

### Hello payload

```
  protocol version   4B u32 LE   always 2
  schema fingerprint 8B u64 LE
  message count      4B u32 LE
  then one 14-byte entry per message:
      message id     4B u32 LE
      field count n  2B u16 LE
      fingerprint    8B u64 LE   the message's own, i.e. prefix n
  length == 16 + 14 * count, exactly
```

### Verdict byte

| Byte | Meaning |
|---|---|
| 0 | accepted |
| 1 | wrong handshake version - the hello layout itself differs |
| 2 | schema conflict - a message both sides know puts different fields at a shared index |
| 3 | malformed hello |
| 4 | not a verdict: a request for more information, and it never ends the session |
| ≥5 | broken |

### How the server decides

The schema fingerprints matching ends it: accepted, without reading a single
entry. Otherwise, for each message id **both** sides declare, with `n_c` the
client's field count and `n_s` the server's:

| | Condition | Result |
|---|---|---|
| a | the two message fingerprints are equal | identical, move on |
| b | `n_c == n_s`, fingerprints differ | verdict 2 |
| c | `n_c < n_s` | compare the client's fingerprint with the server's prefix at `n_c` - equal moves on, otherwise verdict 2 |
| d | `n_c > n_s`, `n_s > 0` | undecidable: ask for the client's prefix at `n_s` |
| d | `n_c > n_s`, `n_s == 0` | the empty prefix is a prefix of everything, move on |

That is RFC-0002 §9.1's prefix test written out in bytes: comparing at
`k = min(n_c, n_s)` asks exactly whether the shorter field list is an exact
prefix of the longer one.

**Different schemas are still accepted.** The condition is not "identical", it
is "wherever the two overlap, they agree". A peer that knows messages the other
does not, or carries extra fields at the end of a shared message, connects
normally - RFC-0002 §9.1 *requires* those peers to interoperate. Only two
different fields at the same index inside the shared part are refused, and one
such message refuses the whole session.

### The prefix chain

A message with `n` fields has `n` prefix fingerprints; entry `k-1` covers its
first `k` fields, and the last entry is the message fingerprint itself. The
chain never goes on the wire - each side keeps its own, and only one value plus a
field count is sent. Only branch d needs a value the peer alone can compute, and
only then is there a second round.

`fomoxac` generates these values (`FOMOXA_SCHEMA_FINGERPRINT`,
`FOMOXA_MESSAGES`, each message's `_PREFIXES`); `MessageSchema::new(id,
fingerprint, prefixes)` is where you hand them over. This crate compares them and
never computes them - how they are derived belongs to the schema layer.

Three rules that keep the exchange bounded:

1. At most one query per session.
2. A client that receives a second query treats the session as broken.
3. The client's handshake deadline covers the whole exchange and is **not** reset
   by the extra round.

### Timers, and why the two roles differ

| Parameter | Default | Meaning |
|---|---|---|
| `handshake_timeout` | 5s | client: a hard deadline on the whole handshake. server: the silence window while a peer has not finished |
| `heartbeat_interval` | 5s | how long a peer may be silent before it is probed |
| `heartbeat_timeout` | 15s | how long a probe may go unanswered before the peer is declared dead |

A client mid-handshake has no heartbeat at all - it has a hard deadline and is
waiting for exactly one thing. A server does have one for every peer, because it
must tell "still computing" from "vanished". A client that answers probes without
ever sending a valid hello can hold a server slot indefinitely: that is the
specified behaviour, and no implementation may invent an absolute cap.

## Heartbeat

Probe **on silence**, never on a timer:

```
  NORMAL  --- silent for heartbeat_interval ---> send exactly one PROBE
     ^                                                |
     |                                            PROBING
     |                                                |
     +--- any valid frame arrives ---------------- unanswered for
          (DATA, PROBE, ACK, HANDSHAKE)             heartbeat_timeout
                                                        |
                                                        v
                                                   peer declared dead
```

Two consequences: a peer with traffic flowing is never probed at all, and nobody
is ever cut off without being probed first. Worst-case detection is
`heartbeat_interval + heartbeat_timeout`, 20 seconds by default. An `ACK` is sent
from inside the tick, whether or not the application ever looks at the event.

## The tick

One tick does four things, in this order, and the order is not negotiable:

```
  0. the CONNECTED event, once in a session's life
  1. push out whatever is still stuck   <- before anything else: wire order is absolute
  2. drain arriving frames, up to max_frames_per_tick
  3. run the protocol clocks            <- handshake deadline, probe, declare dead
  4. hand the event list to the application
```

Nothing blocks. Nothing sleeps. Nothing spawns a thread. `tick(now)` takes the
timestamp as a parameter - `tick_now()` is the convenience wrapper - which is why
the tests run a full expiry cycle without waiting for a real second to pass.
Time comes from `Instant`, which is monotonic; a wall-clock jump can never expire
a handshake or kill a live peer.

### Events

| Event | Raised when |
|---|---|
| `Connected` | the first tick, always, even on UDP where nothing "connects" |
| `Ready` | verdict 0 arrived (client) or was sent (server). Only now may the application send |
| `HandshakeFailed(reason)` | verdict 1/2/3, a broken handshake payload, or the deadline |
| `Message { id, payload }` | a DATA frame while ready |
| `Probe` / `Ack` | a PROBE or ACK frame while ready |
| `Disconnected(reason)` | the transport closed or broke, or the peer stopped answering |

**Exactly one terminal event per session.** If a handshake failed, no
`Disconnected` follows it, even if the transport dies a moment later.

**Payload lifetime:** `Event::Message`'s payload borrows an internal buffer that
the next `tick()` on the same session overwrites. The borrow checker enforces
this - the event iterator holds the connection - so keeping data longer means
copying it out. This is the borrowed form the guide allows; other Fomoxa SDKs
may hand you owned data instead.

Sending is refused, never queued, in three cases: `NotReady` before the verdict,
`Congested` while a frame is still stuck, and `TooLarge` when the transport
cannot carry it. `TooLarge` does **not** kill the session, and the frame is not
retried.

## Writing a transport

A transport moves bytes and reports what happened, immediately. It never blocks,
never spawns a thread, never calls back into the runtime, never interprets a
byte, and never adds a header of its own.

```rust
pub trait Transport {
    fn kind(&self) -> TransportKind;              // Stream or Message
    fn send(&mut self, bytes: &[u8]) -> SendOutcome;
    fn recv(&mut self, buffer: &mut [u8]) -> RecvOutcome;
    fn close_soft(&mut self);
    fn close_hard(&mut self);
}
```

| Outcome | Guide symbol | Meaning |
|---|---|---|
| `SendOutcome::Sent` | ✔ | every byte was taken |
| `SendOutcome::WouldBlock` | ⏸ | **no** byte was taken; ask again next tick |
| `SendOutcome::TooLarge` | ⊘ | this frame will never fit. Do not retry, do not kill the session |
| `SendOutcome::Closed` / `Error` | ✖ / ⚠ | the peer closed cleanly / the link broke |
| `RecvOutcome::Received(n)` | ✔ | a stream may return any number of bytes; a packet transport must return exactly one whole frame |
| `RecvOutcome::WouldBlock` | ⏸ | nothing to hand over yet |
| `RecvOutcome::NeedCapacity(n)` | ⤢ | the buffer is too small; **keep the packet**, the runtime grows and asks again in the same tick |
| `RecvOutcome::Closed` / `Error` | ✖ / ⚠ | as above |

Declare `TransportKind::Stream` and the runtime inserts its own framing layer;
declare `TransportKind::Message` and you are promising one whole frame per
`recv`, never half of one. If the transport distinguishes text from binary
payloads, always choose binary - a Fomoxa frame is not valid UTF-8.

`SendOutcome::Partial(n)` is the one addition this crate makes to that
vocabulary, and it is what the guide's "declare yourself a byte stream and let
the core deal with it" means in practice: a stream transport that accepted the
first `n` bytes says so, and the runtime finishes the rest at the top of the next
tick, before any other frame goes out. A packet transport must never return it.

The other place this crate is explicit: a control frame produced while a frame is
already stuck is appended behind it rather than dropped or overtaking it. Wire
order is absolute, and control frames are rare and tiny. Application sends are
still refused with `Congested`, so nothing queues without bound.

Built in: `TcpTransport` and `TcpListenerTransport` (stream), `UdpTransport`,
`UdpServerTransport` and `UdpPeerTransport` (message). All non-blocking, all on
`std::net`. WebSocket, TLS and QUIC belong in their own crates and need no change
here.

| Quantity | Cap | Source |
|---|---|---|
| one message payload | 16 MiB | every Fomoxa implementation |
| one DATA frame | 16 MiB + 11 B | |
| one HANDSHAKE payload | 1 MiB | allocation guard |
| messages declared in a hello | 1 000 000 | checked before any multiplication, so a hostile count cannot overflow |
| query rounds per session | 1 | |
| frames processed per tick | `max_frames_per_tick`, 64 | tick fairness; the rest arrives next tick |
| UDP datagram | 65 507 B | over that, `send` answers `TooLarge` |

## Conformance

RFC-0003's vectors test a codec, and the codec is `fomoxac`'s - so that suite
lives there, run against the generated code that actually ships. Nothing in this
repository re-answers it.

What this repository's own suite proves is the layer above, against the
implementation guide's own checklist: `framing.rs` (byte-for-byte frame
layout, a stream fed one byte at a time, poisoning, the caps), `handshake.rs`
(all four decision branches, both query outcomes, every malformed shape),
`heartbeat.rs` (a full expiry cycle without waiting), `runtime.rs` (blocked
transports, partial writes, `NeedCapacity`, `TooLarge`, the tick budget, one
terminal event), `interop.rs` (real TCP and UDP sockets, both directions,
including a handshake that needs the second round), and `demo.rs` (a
`fomoxac`-generated codec carried over a real socket, both ways, model in and
model out).

Two of those handshake cases carry RFC-0003 §8.6 up into this layer: a peer that
appended a field at the end, and a peer that dropped one from the end, both
connect. V-001 and V-002 say those peers MUST NOT be rejected, and a handshake
that refused them would break the guarantee the codec below it keeps.

Cross-implementation checking - RFC-0003 §12's X-001…X-003 - is not something a
single repository can run. Byte equality with another SDK is the only proof that
matters there.

## What this crate does not do

No reordering, no retransmission, no deduplication, no encryption, no
compression, no checksums, no matchmaking, no prediction. Over TCP you inherit
ordering and integrity from the transport; over UDP packets may be lost,
reordered or duplicated and are handed up exactly as they arrived. Heartbeat and
dead-peer detection work identically on both, because they run on a clock rather
than on sequence numbers.

Reconnection is the application's decision. A transport that quietly reconnects
itself would leave the two ends disagreeing about whether the session is alive.

## Layout

```
src/frame.rs        frame envelope, packet decode, incremental stream decoder
src/schema.rs       the schema table a handshake compares
src/handshake.rs    hello, verdict, query, reply, and the server's decision
src/session.rs      the transport-agnostic state machine and its clocks
src/event.rs        events, and the arena their payloads live in
src/connection.rs   the tick loop binding a session to a transport
src/server.rs       many sessions, one listener
src/transport/      the Transport trait, TCP and UDP
examples/demo/      one annotated model, and the tree fomoxac wrote from it
```

`session.rs` knows nothing about sockets: frames in, frames and events out, and
every timestamp passed from outside. That is what makes the whole expiry
behaviour testable, and it is why the transports are as small as they are.
